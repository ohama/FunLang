# Build & Test Issues

This document records issues encountered during the build and test process.

---

## FsLexYacc Migration Issues

### 1. FS0222: Module Declaration Missing

**Status:** Resolved

**Error:**
```
src/FunLang/Parser.fs(3,1): error FS0222: Files in libraries or multiple-file applications
must begin with a namespace or module declaration
```

**Cause:** FsYacc generates Parser.fs without a module declaration when using the `<Module>` metadata in .fsproj.

**Solution:** Use `<OtherFlags>` instead of `<Module>` to pass the --module flag:
```xml
<FsYacc Include="Parser.fsy">
  <OtherFlags>--module FunLang.GeneratedParser</OtherFlags>
</FsYacc>
```

### 2. Duplicate Module Declaration in Lexer.fsl

**Status:** Resolved

**Error:**
```
src/FunLang/Lexer.fsl(2,31): error FS0010: Incomplete structured construct at or before
this point in definition
```

**Cause:** The Lexer.fsl header block contained `module FunLang.GeneratedLexer` which conflicted with the --module flag in .fsproj.

**Solution:** Remove the module declaration from the Lexer.fsl header. The module name is specified via --module flag.

**Before:**
```fsl
{
module FunLang.GeneratedLexer
open FSharp.Text.Lexing
...
}
```

**After:**
```fsl
{
open FSharp.Text.Lexing
...
}
```

### 3. Type Mismatch: char vs byte

**Status:** Resolved

**Error:**
```
src/FunLang/Lexer.fsl(43,59): error FS0001: The type 'char' does not match the type 'byte'
src/FunLang/ParserWrapper.fs(17,52): error FS0001: Type mismatch. Expecting a
'LexBuffer<byte>' but given a 'LexBuffer<char>'
```

**Cause:** FsLex generates a byte-based lexer by default (`LexBuffer<byte>`), but the code was using `LexBuffer<char>.FromString()`.

**Solution:** Add `--unicode` flag to enable char-based lexing:
```xml
<FsLex Include="Lexer.fsl">
  <OtherFlags>--module FunLang.GeneratedLexer --unicode</OtherFlags>
</FsLex>
```

### 4. Compile Order: Lexer Before Parser

**Status:** Resolved

**Error:**
```
src/FunLang/Lexer.fsl(3,14): error FS0039: The namespace 'GeneratedParser' is not defined.
src/FunLang/Lexer.fsl(9,16): error FS0039: The value or constructor 'LET' is not defined.
```

**Cause:** F# requires files to be compiled in dependency order. Lexer.fs depends on token types from Parser.fs, but Lexer.fs was listed before Parser.fs in the .fsproj.

**Solution:** Reorder compile items in .fsproj:
```xml
<ItemGroup>
  <Compile Include="Parser.fs" />   <!-- Parser first (defines tokens) -->
  <Compile Include="Lexer.fs" />    <!-- Lexer second (uses tokens) -->
  ...
</ItemGroup>
```

### 5. Test Files: Module Reference Errors

**Status:** Resolved

**Error:**
```
tests/FunLang.Tests/LexerTests.fs(6,14): error FS0039: The namespace 'Lexer' is not defined.
tests/FunLang.Tests/ParserTests.fs(6,14): error FS0039: The namespace 'Lexer' is not defined.
```

**Cause:** After migration, `FunLang.Lexer` module no longer exists. The `tokenize` function is now in `FunLang.Parser` (via ParserWrapper.fs).

**Solution:** Update imports in test files:
```fsharp
// Before
open FunLang.Lexer
open FunLang.Parser

// After
open FunLang.Parser
open FunLang.GeneratedParser  // For token types like INT, PLUS, etc.
```

### 6. Token Format Changes

**Status:** Resolved

**Issue:** Test expectations needed updating due to token format changes:

1. **EOF token included:** The tokenizer now always includes EOF at the end
2. **Boolean tokens renamed:** `BOOL true/false` → `TRUE/FALSE`

**Solution:** Update test expectations:
```fsharp
// Before
Expect.equal tokens [INT 42] "should be single INT token"
Expect.equal tokens [BOOL true; BOOL false] "booleans recognized"

// After
Expect.equal tokens [INT 42; EOF] "should be INT and EOF"
Expect.equal tokens [TRUE; FALSE; EOF] "booleans recognized"
```

### 7. Generated Files Committed to Git

**Status:** Resolved

**Issue:** `Parser.fs` and `Lexer.fs` are auto-generated by FsLexYacc on every build, but were committed to git.

**Solution:**
1. Add to .gitignore:
```gitignore
# FsLexYacc generated files
src/FunLang/Parser.fs
src/FunLang/Lexer.fs
*.fsi
```

2. Remove from git tracking:
```bash
git rm --cached src/FunLang/Parser.fs src/FunLang/Lexer.fs
```

## Previous Issues (Pre-FsLexYacc)

### 8. FsCheck Property Test: Negative Numbers

**Status:** Resolved

**Error:** Property test "identity function returns input" failed for input `-1`.

**Cause:** The expression `(fun x -> x) -1` is parsed as `(fun x -> x) - 1` (subtraction), not as function application with argument `-1`. Negative numbers are lexed as `MINUS INT`, not as a single negative integer token.

**Solution:** Use `NonNegativeInt` instead of `int` in property tests:
```fsharp
// Before
testProperty "identity function returns input" <| fun (n: int) ->

// After
testProperty "identity function returns input" <| fun (n: NonNegativeInt) ->
```

---

### 9. FsCheck Null Input Crashes Lexer

**Status:** Resolved

**Issue:** FsCheck generated null string input which crashed the lexer.

**Solution:** Added null check in tokenize function.

### 10. Argu --trace Option Conflict

**Status:** Resolved

**Issue:** The `--trace` CLI option conflicted with something in the argument parsing.

**Solution:** Changed to comma-separated format for trace options.

---

### 11. formatValue Function Missing rec Keyword

**Status:** Resolved

**Issue:** The `formatValue` function in Program.fs calls itself recursively for nested values (tuples, lists) but was missing the `rec` keyword.

**Solution:** Add `rec` keyword:
```fsharp
let rec formatValue = function
    | VTuple vs -> vs |> List.map formatValue |> ...
    | VList vs -> vs |> List.map formatValue |> ...
    ...
```
